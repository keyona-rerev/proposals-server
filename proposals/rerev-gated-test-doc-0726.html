What just happened

The gate runs before the static file handler, so an unauthenticated request never touches this file.

  1. GET You requested the documentThe server pulled the slug off the URL and checked it against protected.json.
  2. 401 The gate answered firstSlug is on the protected list, so the server returned a challenge and your browser showed the login prompt.
  3. AUTH Your credentials were comparedAgainst a value held only in Railway, using a timing-safe comparison. Nothing is stored in the repo.
  4. 200 The file was releasedOnly after the match. That's this page.

Confirm it yourself

Three quick checks that prove the gate is real and not decoration.

  • Open the link in a private window. You should be stopped at a login prompt, not the page.
  • Enter a wrong password. The prompt reappears. It does not let you through and does not reveal which field was wrong.
  • Try viewing the page source without logging in. There is nothing to view — the document is never sent, so it can't be read from the network tab or a cached copy.

How the protection is wired

Two pieces, kept deliberately separate.

The repo says what is protected. protected.json lists the slugs that require a login. That's all it holds — a list of names.

Railway holds who can get in. Each protected slug reads one environment variable named GATE_<SLUG> containing the username and password. Credentials are never committed and never appear in the HTML.

It fails closed. If a document is listed as protected but its credentials are missing, the server refuses the request instead of serving it openly. A protected page cannot accidentally become public.

To share this document, send the link, the username, and the password separately from each other.
